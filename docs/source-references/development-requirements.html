范围与边界

先划掉一半

一句话目标：用户打开 App 时不被开屏广告挡住，被广告骗点或误触跳转时能一键退回；同时能对任意 App 出一份可举证的广告体检报告。三件事都由同一个无障碍服务加同一套规则引擎支撑，不引入第二套技术栈。

v1.0 做与不做

v1.0 要做v1.0 明确不做（及原因）
开屏广告自动跳过（按包名 + 场景路由）不做 iOS：无对应无障碍自动化能力，苹果审核指南也明禁改原生 UI
插屏 / 浮层 / 弹窗广告的关闭不做 HTTPS 解密与根证书：证书固定 + 合规风险，且广告与内容同域时本就无解
误触防护：跨应用跳转检测 + 一键返回不承诺“全 App 去广告”：规则覆盖率是概率，承诺即失信
规则包静默更新（验签 + 灰度 + 回滚）不做默认全局开启：首次必须逐应用授权，默认只开体检
广告体检 23 项、评分定级、报告导出不做 UGC 规则市场：审核与责任边界撑不住，v1.1 再议
本地遥测聚合 + 匿名上报（可关）不做 B 端审计版：另立产品线，不占 v1.0 工期

角色与使用场景

6 个主场景

只有一类用户，三种身份状态：刚装上还没授权（游客）、开了无障碍（普通用户）、再装了 Shizuku 或 root（进阶用户）。不做账号体系，不做登录，订阅只认设备与购买凭证。

编号场景触发与期望结果失败时用户的感受
S1冷启动跳过开屏用户点开某 App，广告层出现后 800ms 内被关闭，进入首页“开了但没跳过”——比没装还糟，必须能在设置里看到这条规则的命中记录
S2关闭插屏浮层浏览中弹出插屏，识别到关闭控件并点击，返回原页面点错位置进了落地页，用户要么以为是自己手抖，要么直接卸载
S3误触跨应用跳转用户点击导致前台包名跳变，500ms 内弹出悬浮确认条，一键返回原 App被拉去应用商店/电商页，且无法一键退回——这是最伤的一类
S4规则包静默更新后台拉取、验签、原子替换，全程不打扰；失败保留旧包更新后规则全失效，用户看到“昨天还能跳，今天不行了”
S5广告体检用户选定 App，自动 + 半自动跑 23 项，出一份带证据的报告报告结论无法复核，或把“未验证”写成“达标”——信用一次性归零
S6无障碍被系统回收检测到服务断开，通知栏提示 + 一键重新授权，不反复弹窗用户以为软件坏了，实际是系统每 24 小时回收一次

功能需求

FR-01 … FR-42

优先级只有三档：P0 v1.0 必须，缺了不能发版；P1 v1.0 应有，工期紧可顺延一周但不跨里程碑；P2 明确不做，登记在技术债。编号一经分配不复用，删需求就把编号留空。

A 组 · 授权与引导（5 条）

编号需求与实现要点优先级验收口径
FR-01首次启动引导：三步说明“为什么需要无障碍、能看到什么、数据不出设备”，第三步才跳系统设置页。不得用全屏遮罩强迫授权，必须可跳过P0可跳过且跳过后再不主动弹；设置页内可随时回来开启
FR-02无障碍服务声明：accessibilityService 的 description 与 config 明确用途，canRetrieveWindowContent=true，事件类型只订阅 TYPE_WINDOW_STATE_CHANGED / TYPE_WINDOW_CONTENT_CHANGED，不订阅全部P0抓包与日志确认只收到两类事件；系统设置页显示的用途文案与隐私政策一致
FR-03逐应用授权：首次在某个 App 上生效前，弹一次“是否允许在此应用内处理广告”，默认关闭，勾选后写入 app_cfg.enabledP0新安装的 App 一律不生效，直到用户明确勾选
FR-04授权健康度检测：进入首页时检查服务是否连接、是否被系统限制（部分 ROM 的“受限制的设置”），给出具体到系统路径的修复指引P0四种状态（未授权 / 受限 / 可用 / 被回收）都能正确识别并显示对应文案
FR-05Shizuku 作为第二通道（可选）：检测到 Shizuku 可用时，提供“用 Shizuku 授权”入口，仅用于无障碍不可用时的兜底，不与无障碍双跑P1两条通道互斥，切换时不产生重复点击

B 组 · 采集与识别（6 条）

编号需求与实现要点优先级验收口径
FR-06窗口事件采集：收到窗口变化后，取 event.packageName + event.className + 根节点，判定“是否为新开屏”：冷启动 6 秒窗口内 + Activity 名含 splash/广告容器特征 + 根节点面积占屏 ≥ 70%P010 个目标 App 各冷启动 10 次，识别率 ≥ 90%（W0 口径复现）
FR-07节点树快照：把当前窗口树序列化为扁平列表（含 bounds、text、contentDesc、clickable、enabled、visible、层级路径），供调试器与规则求值共用P0同一棵树导出的 json 在桌面查看器里坐标与截图逐节点对齐
FR-08受限遍历：深度 ≤ 12、节点 ≤ 400、单次耗时 ≤ 800ms、仅 isVisibleToUser 节点；超出预算立刻返回已采集部分，不抛异常P0构造 5000 节点的极端页面，遍历在 800ms 内返回且不重启服务
FR-09自绘控件降级：当窗口树有效节点 ≤ 3 且总面积 < 屏 30%，标记 opaque=true，落库时记录该标记并在体检报告中单列覆盖率P0H5 / Flutter 广告页能被识别为 opaque，且不影响其他 App 的正常处理
FR-10屏幕内容不出设备：text / contentDesc 只在本进程内存中参与匹配，禁止写入日志、禁止进数据库明文、禁止上报P0审查全部日志与落库字段；抓包确认上报体中不含任何屏幕文本
FR-11调试器：开发者模式下可导出当前窗口树 json + 截图 + 设备信息（ROM、版本、分辨率、密度），一键生成可提交的规则草稿P1从导出到生成一条可用规则 ≤ 5 分钟，不需要连电脑

C 组 · 规则引擎（9 条）

编号需求与实现要点优先级验收口径
FR-12JSON5 解析与 schema=3 校验：逐字段检查类型与必填，单条规则不合法只剔除该条，整包仍可加载P0构造 5 种坏规则（缺字段 / 类型错 / 正则未闭合 / ver 不匹配 / 字段拼错），全部被拒且不影响同包其他规则
FR-13选择器求值优先级：rid 精确命中优先，其后依次是文本正则、desc、cls；同级别取面积最小、离指定边最近的；只认 visible 且 enabled 的节点P0同一棵树上给出 3 个候选，稳定命中同一个；换机型后命中率不减
FR-14动作执行：click（不可点时向上找可点击祖先，最多 3 层）、back、none；点击后 300ms 内复核目标是否消失P010 条规则连续 3 天命中率 ≥ 90%，零次点进落地页（W3 口径）
FR-15安全闸门（三步，任一不过即放弃）：前台包名与根节点包名一致 → 包名不在硬编码白名单（金融 / 支付 / 政务 / 系统设置）→ 目标控件文案不含敏感词（同意 / 授权 / 允许 / 支付 / 确认 / 绑定 / 登录）P05 个银行/支付类 App 全部无法被接管；敏感词命中时 100% 放弃并记 skipped
FR-16冷却与频次：同包名同场景 cooldownMs 默认 1500、单会话 maxPerSession 默认 1、全局 10 分钟内不超过 8 次P0连续触发不会连点；超频时只记数不执行
FR-17verify=both 双校验：点击后要求「目标控件消失」且「前台包名未变化」，任一不满足即判 negative 并触发该规则降权P0人工造假的规则（点了不关闭）会被判 negative，不影响用户
FR-18结果落库：每次求值写一条 hit（positive / negative / skipped，含 cost_ms、rule_id、时间片），未命中也记一条P0可从数据库还原任意一次处理链路；cost_ms 与实际耗时误差 < 5ms
FR-19规则热加载：订阅包更新后原子替换内存规则表，不重启服务、不中断监听P0更新期间连续触发 20 次，无一次落在半成品规则集上
FR-20异常兜底：求值、点击、落库任一步抛异常都在单次调用内捕获，记 error 计数并继续监听，绝不崩溃或退出P0注入 20 类异常（空节点、越界、并发修改），服务存活率 100%

D 组 · 规则分发（5 条）

编号需求与实现要点优先级验收口径
FR-21拉取策略：GET /manifest.json，带 ETag 与 If-None-Match，超时 5s；失败按 6h / 12h / 24h 退避，不无限重试P0断网 24 小时后恢复，首次打开即完成一次拉取，且退避期间无后台唤醒
FR-22签名校验：Ed25519 验签，公钥内置 APK，sig 覆盖除自身外全部内容；验签失败整包丢弃，保留旧包并记一次失败P0篡改一个字段的包 100% 被拒；连续 3 次失败暂停拉取 24h
FR-23双通道：stable / beta，用户可在设置切换，切换立刻重新拉取（仍走验签）P1切换后 1 分钟内拿到对应通道版本，且回切不残留
FR-24原子替换与回滚：先写临时目录 → 全量校验 → 切换指针；保留上一版可回滚，回滚后规则集与替换前逐条一致P0故意推一版错误规则，10 分钟内回滚且客户端不崩
FR-25接入 ruleCheck CI：字段缺失 / 正则未闭合 / ver 与 pkg 不符 / 同 Activity 两条 match 相交，四类失败阻断发布P0四类各造一个样例，全部在 CI 阶段失败，不允许打进订阅包

E 组 · 误触防护（4 条）

编号需求与实现要点优先级验收口径
FR-26包名跳变检测：前台包名 A → B，且触发点击落在广告区域内（非用户主动导航），判为误触；用户主动切 App 不拦P0模拟 5 种拉起场景，拦截率 ≥ 80%，误拦低于 1/50 次
FR-27悬浮确认条：跳转后 500ms 内显示，5 秒倒计时，文案「你被带到了 XX，返回 原App」，可手动关闭P0不遮挡跳转后页面的关键操作；倒计时结束自动消失不留残影
FR-28一键返回：点击后用 back 栈回到原 App 的同一页面，不新起 ActivityP0返回后页面状态与原页面一致（滚动位置、输入内容不丢）
FR-29_shared/jumpGuard.json5 通配规则：以包名白名单方式覆盖未单独配置的 App，避免为每个 App 写一条P1通配规则不覆盖用户手动关闭的 App；与个别规则冲突时个别规则优先

F 组 · 广告体检（5 条）

编号需求与实现要点优先级验收口径
FR-30检测项落地：v1.0 只做 12 项自动 + 8 项半自动的采集侧，人工 3 项（摇一摇阈值、设置页开关、强制下载）在报告中标「未验证」，不得写成达标P0对 10 个 App 出具报告，每条结论都能被人对着屏幕复核
FR-31评分与定级：100 − 15×严重 − 6×高 − 2×中（下限 0），未验证项不计分单列；严重 ≥ 1 即 D 一票否决P0构造三组样本（含 1 严重 / 0 严重多高 / 全中），评级结果与手算一致
FR-32覆盖率：覆盖率 = 有效项 / 23，含 opaque 页面的单独标注；低于 80% 时评级后加「覆盖不足」且禁用导出P0opaque 页面覆盖率被单列，不混进总体；< 80% 时导出按钮确实不可用
FR-33证据四件套：带时间戳截图、节点树 json、复现步骤（设备/网络/版本/冷启动轮次）、引用条款原文；工程口径（24dp、3:1、1500ms）单独标注为「工程口径」P0任取一条结论，四件套齐全，条款引文与现行文本逐字一致
FR-34报告导出与举报引导：本地生成 PDF / 长图，附 12315、12321、属地市监三条渠道与「材料清单」；报告页写明「本报告为举报线索，不构成违法认定」P1导出的 PDF 在无本 App 的设备上可正常打开；免责声明不可关闭

G 组 · 遥测与隐私（4 条）

编号需求与实现要点优先级验收口径
FR-35本地聚合：按「包名哈希 × 规则 × result × 天」聚合计数，明细保留 90 天后只留聚合结果P0数据库体积在重度使用 30 天后 < 20MB
FR-36匿名上报：字段白名单（rule_id / pkg_hash / result / cost_ms / ver_code / rom / 日期），无设备标识、无屏幕文本；默认开启但可一键关闭P0抓包逐字段核对，无一项超出白名单；关闭后立即停止发送
FR-37失效告警：单条规则连续 3 天 negative 占比 > 40% 时，本地标记为「可能失效」并在设置页提示「等待规则更新」P1人为制造失效（改 App 版本），3 天内状态变为可能失效
FR-38隐私开关与清除：一键清除本地全部数据（规则保留内置版）、随时关闭遥测、查看已上报内容摘要P0清除后数据库为空、规则集回到内置版本、不残留缓存文件

H 组 · 设置与运维（4 条）

编号需求与实现要点优先级验收口径
FR-39设置页能力：总开关、逐应用开关列表（按最近使用排序）、规则包版本与通道、命中统计（今日/近 7 天）、日志导出P0每个开关都能即时生效，不需要重启服务
FR-40命中记录：按 App 展示最近 20 次处理（时间、规则、结果、耗时），可单条回看截图（若已保存）P1用户能自己回答「为什么这个 App 没跳过」

数据模型

Room · 5 张表

只有五张表，够用且便于审查。凡是可能含屏幕文本的字段，一律不进库——规则匹配用的字符串只在内存里活一次。

app/schemas · Roomschema 变更需迁移脚本
rule(id TEXT PRIMARY KEY,        // "com.zhihu.android/splash-01"
     pkg TEXT, scene TEXT, rev INT,
     ver_range TEXT, json TEXT,
     status TEXT,                // active / deprecated / removed
     source TEXT,                // builtin / stable / beta
     updated_at INT)

hit(id INTEGER PRIMARY KEY AUTOINCREMENT,
     ts INT, day TEXT,           // day = yyyymmdd，聚合用
     pkg TEXT, activity TEXT,
     rule_id TEXT,
     result TEXT,                // positive / negative / skipped
     cost_ms INT, opaque INT, session_id TEXT)

app_cfg(pkg TEXT PRIMARY KEY, enabled INT,
     guard_level INT, last_seen_at INT)

report(id TEXT PRIMARY KEY, pkg TEXT, ver_code TEXT,
     score INT, grade TEXT, coverage REAL,
     created_at INT, payload TEXT)

rule_pack(channel TEXT PRIMARY KEY,   // stable / beta
     version TEXT, sig_ok INT,
     applied_at INT, rollback_from TEXT)

-- 索引：hit(pkg, ts) · hit(rule_id, ts) · hit(day)

保留与清理

数据保留策略说明
hit 明细90 天或 5 万行，先到先清超限时按天聚合后删除明细，聚合结果保留 180 天
report最近 20 份超出后按时间淘汰；正在编辑的不参与淘汰
运行日志7 天或 2MB环形缓冲，禁止写入 text / contentDesc
崩溃栈最近 50 条脱敏后才落盘，用户主动上报才发送
规则包当前 + 上一版上一版用于回滚，其余版本直接删

原子性临时目录写入 → 全量校验 → 切换指针；任一步失败保留原状并记录失败原因

非功能需求

上线门槛

这些数字不是“优化目标”，是准入门槛。任一不达标就不能发版，因为去广告工具的失败方式是“用户觉得手机变卡了”，而不是报错。

类别阈值测量方法
冷启动额外耗时P95 < 80ms引擎首次初始化埋点，只在进程冷启动统计，不含系统无障碍唤醒时间
单次处理耗时P95 < 300ms从收到窗口事件到动作执行完成
单次遍历 CPU< 15msThreadMXBean 采样，节点 400 的标准树
待机日耗电< 2%24h 静置，前台服务 + 常驻通知开启，Battery Historian 读数
内存增量< 30MB空闲态 PSS 对比无服务时
崩溃率< 0.2%会话崩溃比，灰度 500 人阶段统计
APK 体积< 12MB含内置规则包，不含订阅包
兼容范围Android 9–16minSdk 28；四家 ROM（澎湃 / ColorOS / OriginOS / 原生）各至少一台真机回归
离线可用必须无网络时用内置规则集，功能不降级、不弹错误
无障碍不可用零崩溃服务被关闭 / 被限制时，App 本身正常运行，只做能力降级提示

状态机

3 个

三个状态机必须显式实现，不要用散落的布尔变量拼。规则失效、授权被回收、冷却超时，这三处是 bug 高发区。

状态机当前状态触发转移与动作
规则active连续 3 天 negative 占比 > 40%→ deprecated，设置页提示「等待规则更新」，不再参与求值
规则deprecated新版本 positive 恢复→ active，重置计数
规则deprecated7 天未恢复→ removed，进入 removed 列表，客户端删除本地副本
授权未授权用户在系统设置开启→ 可用，初始化规则表并注册事件监听
授权可用ROM 判定为受限设置→ 受限，只提示修复路径，不反复弹窗
授权可用 / 受限系统回收服务→ 回收，发一条通知，用户点击后回到未授权
会话idle窗口事件到达且场景命中→ detecting，开始受限遍历
会话detecting求值命中且安全闸门通过→ acting，执行动作并进入 cooling
会话detecting未命中 / 闸门拒绝→ idle，记一条 negative 或 skipped
会话cooling冷却到期且前台未变→ idle，等待下一次事件
一处容易漏的地方：求值失败和闸门拒绝都算“看过但没动手”，必须落库成 negative / skipped。不记的话，命中率分母会变成“只统计成功的那部分”，遥测数据会系统性偏高，规则优化就失去依据。
