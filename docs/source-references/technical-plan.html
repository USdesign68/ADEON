技术方案 · v1.0 · 2026-11-06

开屏净化助手

一个只做 Android 的本地规则引擎：在应用启动的那几秒里，把该点的“跳过”点掉，把不该发生的跳转拦下来。本文给出分层架构、规则文件格式与十周排期，可以直接照着开工。

目标平台
Android 12 及以上（API 31+），单端
技术栈
Kotlin + AccessibilityService，JSON5 规则，无 Root
工程量级
1 名开发 10 周出 v1.0

一次开屏的完整时序

从事件产生到结果落库，全程在本机完成，最长不超过 800 毫秒；任何一步不满足就立即放弃，不做重试。

01
窗口切换事件TYPE_WINDOW_STATE_CHANGED → 记录包名与 Activity
02
版本路由包名 + Activity 匹配规则集，校验 minAppVer / maxAppVer
03
安全闸门当前前台包名 == 规则包名？白名单？会话冷却中？
04
受限遍历800ms 窗口内一次 DFS，深度 ≤ 12，节点 ≤ 400，超限即止
05
选择器求值多命中时取可点击祖先 + 面积最小 + 文本权重最高者
06
敏感词复核命中节点文案含“同意 / 授权 / 支付 / 确认 / 绑定”即放弃
07
执行动作click → 校验窗口是否已切走；未切走则按规则决定 back 或放弃
08
结果落库记录 命中 / 未命中 / 误触回滚，本地聚合后匿名上报规则 id

规则文件格式

JSON5 · 纯数据 · 可热更新

引擎不认识任何具体应用——它只认规则。新增一个 App 的支持、修一条失效的选择器，都只是加一个文件、推一次订阅，不需要发版。这是这套方案能不能长期维护下去的关键。

目录结构androidApp/src/main/assets/rules
rules/
  index.json5              // 包名 → 规则清单、文件校验和、最低客户端版本
  com.zhihu.android/
    splash.json5
    interstitial.json5
  _shared/
    jump-guard.json5       // 跨应用通配规则，pkg = "*"

文件命名固定为 <pkg>/<scene>.json5，scene 只有四个取值：splash、interstitial、dialog、jumpGuard。一个文件可含一条或多条规则，但同一 scene 下的规则共享同一份版本区间。

顶层字段

字段类型约束说明
schemaint必填固定为 3。低版本规则由引擎启动时迁移，不做长期兼容。
idstring必填<pkg>/<scene>-<序号>，全局唯一。它同时是遥测主键，改名等于丢历史数据。
pkgstring必填目标包名。通配规则写 "*"，仅允许 jumpGuard 场景使用。
namestring必填中文短名，展示在规则列表里，不超过 16 字。
revint必填修订号，单调递增。灰度时用它与线上版本做差异比对。
verstring必填宿主版本区间，">=8.2.0 <10.0.0"。不在区间内直接跳过，不做降级尝试。
sceneenum必填splash / interstitial / dialog / jumpGuard。
whenobject必填触发条件，见下表。
matchobject必填匹配条件，见下表。
actobject必填命中后的动作，见下表。
guardobject选填冷却与限频。缺省取引擎默认值，不建议在规则里放开频次。
tagsstring[]选填分组标签，用于按渠道、人群灰度。

when / act / guard

键类型约束说明
when.activitystring[]必填Activity 名，支持通配，如 "*.SplashActivity"。空数组视为匹配任意界面，仅限 jumpGuard。
when.elapsedMaxint选填冷启动后多少毫秒内有效，默认 6000。0 表示不限。
when.stayMsint选填界面出现后等待多久再动作，默认 120。用来避开首帧渲染，防止点到还没画完的占位图。
when.firstLaunchOnlybool选填仅冷启动首次生效，默认 true。
when.pkgSwitchWithinint选填只有当前台包名在 N 毫秒内发生过切换时才生效。这是 jumpGuard 的防误判开关，别省。
act.typeenum必填click / back / wait / none。none 用于只采集不动作的观察期规则。
act.targetstring选填self / parent(n) / sibling(n)，默认 self。上溯最多 3 层。
act.waitMsint选填动作执行后等待毫秒，默认 0。
act.verifyenum选填动作后如何判定成功：windowChanged / nodeGone / both，默认 windowChanged。
guard.cooldownMsint选填同一规则的最小触发间隔，默认 1500。
guard.maxPerSessionint选填单次前台会话最多执行次数，默认 1。
guard.maxPerDayint选填单日上限，默认 24。超过即静默停用并上报。
guard.requireForegroundbool选填执行前必须确认前台包名等于规则包名，默认 true，不要关。

匹配选择器

键类型约束说明
anyselector[]必填至少一条，任一命中即视为匹配。按数组顺序求值，先命中先返回。
allselector[]选填全部满足才执行。典型用法：用 maxArea 排除整屏可点容器。
tstring选填文本正则，必须 ^...$ 全量锚定。裸关键词会命中“跳过并领取会员”。
ridstring选填resource-id，支持 *:id/splash_skip 与 close_* 两种通配写法。
clsstring选填类名，支持 | 并列与后缀通配。用来区分图标按钮与文字按钮。
descstring选填contentDescription。无文字的无障碍友好按钮常靠它命中。
depth[int,int]选填相对窗口根的层级闭区间，如 [2,8]。收窄遍历范围，省电。
maxAreaint选填节点面积上限（dp²）。开屏跳过按钮通常 < 6000，超过基本是全屏蒙层。
withinstring选填距屏幕某边的最大距离，如 "top:200"、"right:120"。跳过按钮几乎总在右上角。

三条真实规则

com.zhihu.android/splash.json5scene = splash
{
  schema: 3,
  id: "com.zhihu.android/splash-01",
  pkg: "com.zhihu.android",
  name: "知乎 · 开屏跳过",
  rev: 7,
  ver: ">=8.2.0 <10.0.0",
  scene: "splash",

  when: {
    activity: ["*.SplashActivity", "*.activity.WelcomeActivity"],
    elapsedMax: 6000,      // 只在这 6 秒里管，超时放手
    stayMs: 150,
  },

  match: {
    any: [
      { t: "^跳过\\s*\\d*$", cls: "TextView|Button", within: "top:200" },
      { rid: "*:id/splash_skip" },
    ],
    all: [
      { maxArea: 6000 },     // 排除整屏可点蒙层，防止误点进落地页
    ],
  },

  act: { type: "click", target: "self", verify: "windowChanged" },
  guard: { cooldownMs: 1500, maxPerSession: 1 },
  tags: ["social"],
}
com.example.news/interstitial.json5scene = interstitial
{
  schema: 3,
  id: "com.example.news/interstitial-02",
  pkg: "com.example.news",
  name: "资讯 · 插屏关闭",
  rev: 3,
  ver: ">=6.4.0",
  scene: "interstitial",

  when: { activity: ["*.MainActivity"], stayMs: 300 },

  match: {
    any: [
      { t: "^关闭|跳过$", cls: "ImageView|TextView", maxArea: 3600 },
      { rid: "*:id/interstitial_close" },
    ],
  },

  act: {
    type: "click",
    target: "parent(1)",   // 图标本身不可点，上溯一层找容器
    waitMs: 800,
    verify: "both",        // 窗口切走 + 节点消失，双条件才算成功
  },
  guard: { maxPerSession: 3, maxPerDay: 12 },
}
_shared/jump-guard.json5scene = jumpGuard，pkg 通配
{
  schema: 3,
  id: "_shared/jump-guard-01",
  pkg: "*",                  // 仅 jumpGuard 允许通配
  name: "落地页 · 拉起浮层关闭",
  rev: 5,
  ver: "*",
  scene: "jumpGuard",

  when: {
    activity: ["*"],
    pkgSwitchWithin: 800,    // 前台包名刚换过，才可能是广告落地页
  },

  match: {
    any: [
      { t: "^打开.{0,6}(APP|App|应用)", maxArea: 40000, within: "bottom:600" },
      { t: "^取消|以后再说|暂不", cls: "TextView|Button", maxArea: 20000 },
    ],
    all: [{ maxArea: 120000 }],
  },

  act: { type: "click", target: "self", waitMs: 300, verify: "both" },
  guard: { cooldownMs: 5000, maxPerSession: 2 },
  tags: ["guard"],
}

求值规则（引擎侧硬编码，规则不能覆盖）

  • 多命中的排序：rid 精确命中优先，其后依次是文本正则、desc、cls；同级别取面积最小、离指定边最近者。
  • 只认可见节点：要求 isVisibleToUser 且 enabled。节点不可点时上溯最近的可点击祖先，最多 3 层，仍不可点则放弃。
  • 只求值一次：事件到达后单次求值，不轮询、不重试。未命中也记一条 negative 样本，作为规则优化的输入。
  • 敏感词复核：命中节点文案含“同意 / 授权 / 允许 / 支付 / 确认 / 绑定 / 登录”一律放弃。这条比任何规则优先级都高。
  • 白名单优先于一切：金融、支付、政务、系统设置类包名在引擎层硬编码，规则里写什么都点不进去。
为什么是 JSON5 而不是 protobuf / 二进制：规则要能被社区写、被人肉 review、被 diff 看出改了什么。体积差几十 KB，换来的是可协作——这笔账在规则库这个场景里划算得离谱。

订阅包与校验

public-stable.json5客户端只读、只验签
{
  schema: 3,
  subId: "public-stable",
  name: "公共规则库 · 稳定版",
  ver: 2026110601,          // 日期 + 当日序号
  channel: "stable",        // stable | beta
  minClient: 10000,         // 低于此 versionCode 的客户端不下发
  rules:   [ "com.zhihu.android/splash-01", "com.example.news/interstitial-02" ],
  removed: [ "com.foo.bar/splash-03" ],
  sig: "ed25519:9f2c...",   // 对除 sig 外的全部内容签名
}

客户端拿到订阅包后的顺序固定为：验签 → schema 版本检查 → 逐条跑 ruleCheck → 与本地白名单做冲突检测 → 原子替换。新版本先写临时目录，全部通过才切换指针，任何一步失败保留旧版本并记录失败原因。这条链路决定了“规则推错一次会不会把用户搞崩”。

规则校验器CI 门禁
./gradlew ruleCheck -Ppkg=com.zhihu.android -Pstrict

# 四类失败：
#  1. 字段缺失 / 类型不符 / schema 版本不匹配
#  2. 正则未全量锚定，或存在灾难性回溯风险（嵌套量词）
#  3. ver 区间与 pkg 实际版本对不上
#  4. 同一 Activity 下两条规则的 match 相交（会互抢点击）
# strict 模式下任一失败即拒绝构建，不允许带病进订阅包。

排期：W0 门控 + 十周

单人 · 每周一个可验收产物

排期的唯一原则是每周结束时手上有一个能被验证的东西，而不是“完成了百分之多少”。规则引擎这类产品最容易死在“写了两周还没法在真机上跑”上，所以第一周就必须产出可用的节点树调试器。

W0 · 前置验证周 —— W1 之前，5–10 天，不写功能代码

十周排期成立的前提只有两条：开屏窗口在主流 ROM 上能被稳定识别，一条规则能端到端跑通。这两个假设不成立，后面九周的引擎与订阅链路都没有落点。所以先花一周做门控，用真机数据决定要不要开这个工。

四个动作，一个串行、三个并行：

  • P0 真机 PoC（串行，5–10 天）。8–10 台机器（澎湃、ColorOS、OriginOS、原生 Android 各至少 2 台）× 10 个目标 App，每台冷启动 10 次，只记三件事：窗口事件能否捕获且能判定归属包名、从事件到点击的耗时、点击是否落到预期目标。产出是一页 PoC 报告，不是代码。
  • P1 主体与分发决策（并行，3 天）。个人主体开源免费 / 注册公司收订阅 / 海外主体，三选一。它决定 W5 要不要接支付、W10 上哪个商店，拖到后面每改一次都是返工。
  • P2 规则冷启动清单（并行，3 天）。按开屏广告出现率从高到低选 10 个目标 App，每条规则配一个回归用例（版本号 + 截图 + 期望动作）。W4 的“20 条规则”就从这份清单长出来，不是临时凑的。
  • P3 法务与命名口径（并行，3 天）。开源协议（建议 Apache-2.0，不要 GPL 系）、隐私政策里的无障碍用途与“屏幕内容不出设备”声明、名称里不出现“跳过广告”这类功能性描述。
门控项阈值不达标怎么办
开屏窗口识别率≥ 90%，且至少 6 台机型达标先收缩机型范围，或换识别策略（窗口事件 + Activity 生命周期兜底）
单次处理耗时P95 < 300ms把遍历预算压下来再进 W3，不要带病往下走
误点次数100 次冷启动中 0 次未收敛前不加任何新规则，只留点击后校验
W0 的止损线。若两家以上主流 ROM 都做不到“稳定捕获 + 准确归属”，且 Shizuku 通道同样受限，就不要硬推：产品降级为「误触防护 + 广告体检」两条腿，去广告改成一键手动跳过。这两条都不依赖点击注入，也不依赖窗口归属。方案 B 能砍掉 W3–W5 的大部分工作量，把 W7、W8 提前，v1.0 的目标从“自动跳过”改成“广告合规体检 + 误触兜底”。

三个会影响排期的风险

  • 无障碍被系统收紧。ColorOS、澎湃等已经把“受限制的设置”做进系统，用户授权多两层。对策：把 Shizuku 做成第二通道并在引导里讲清楚，不做任何对抗——对抗一次，下个版本就会被封死。
  • 规则维护是长期成本，不是开发工作量。宿主 App 一次改版就能让规则全废。对策：W5 就要把失败率驱动的失效告警跑通，否则后面靠人工发现，永远慢半拍。
  • 合规成本会挤占 W10。APP 备案、隐私政策、开源仓库、送审都是硬门槛，草稿要在 W8 就开始准备，不要压到最后一周。
排期上最该砍的：体检报告的第二、三期功能，以及规则市场（UGC 规则分享）。前者是营收故事，后者是社区故事，都不影响 v1.0 能不能站住。如果时间不够，优先保 W1–W5 的引擎与订阅链路——那是这个产品唯一不可替代的部分。
